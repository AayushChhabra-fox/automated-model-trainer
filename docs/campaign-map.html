Automated Model Trainer · campaign anatomy

One hypothesis, one frozen champion, one honest answer

A campaign moves across three lanes: the human who owns the decision, the agents running in a local LangGraph process, and Databricks doing every unit of compute. Seven checkpoints belong to the human. Only one stretch runs unattended — the Trainer loop inside a single hypothesis — and it ends at a review of that hypothesis's champion.

Human checkpoint Agent step (local CLI) Databricks job → MLflow QA holdout — sealed until freeze

Two evaluation modes, one harness

The contract's evaluation_mode decides what a unit of evaluation is. Everything downstream — the metrics, the paired comparison, the bootstrap, SplitGuard, the freeze — is the same code in both modes.

What QA can say

Phase 0 only

INVALID_EXPERIMENT

The artifact or evaluation path is broken. Fix the defect and rerun Phase 0 — features, hyperparameters and model choice stay untouched. Retries are capped.

Phase 1

PASS

Meets the acceptance criteria set before QA ran. Register as candidate; proceed to online A/B or shadow evaluation.

Phase 1

FAIL_HYPOTHESIS

Won on validation, did not generalise. Recorded as a finding. The same model's search is not reopened with QA feedback.

Phase 1

SPEC_REVIEW

Labels, population, candidates or metrics are wrong — or the proxy-sanity gate failed, meaning the offline metric does not track the product number even for the incumbent. Back to the human.

The report a product owner reads

Every number in the ExperimentationReport comes out of Phase1Result. The Planner writes the narrative around it and never the numbers. A losing campaign gets the same report as a winning one.

  1. Proxy sanity, first. Spearman ρ between the incumbent's daily offline metric and the external product series. Below min_proxy_correlation, or fewer than seven overlapping days, and the campaign is SPEC_REVIEW before a single candidate number is displayed.
  2. The effect in product units. Top-slot conversions per 1,000 renders, candidate against incumbent, with a confidence interval. Under pbm this is a self-normalised estimate whose incumbent value collapses to its own observed rate — so the incumbent's number in the report matches what the dashboard shows, and the candidate's is the counterfactual.
  3. Where it regressed. Paired cohort and segment deltas with intervals, and an explicit list of cohorts worse than the contract's guardrail.
  4. What the weighting did. θ per client × position, printed, so a reader can judge the correction rather than trust it.
  5. What an online test would cost. Baseline rate, offline effect size, MDE at 80 % power, required renders, and days at the rail's own measured traffic.
  6. What this cannot tell you. Replay re-orders the incumbent's own candidate set, so it measures re-ranking and not better retrieval; the PBM comes from the incumbent's logs and not from randomisation; offline improvement is not causal lift.

Where things live

MLflow

Everything about a run

Params, curves, validation and QA metrics, model artifacts, result.json, conclusion.md and report.html. Tagged with campaign, hypothesis, contract_hash, harness version, code version.

Delta tables

Only the ground truth

Materialised split_train, split_validation, split_qa, pinned by Delta version and a membership hash. In grouped_rerank a row is a render carrying its candidates, positions, labels and weights. Source tables are read, never copied per experiment.

Orchestrator state

Just enough to resume

Stage, approvals, hypothesis statuses, approved shapes, budget, run IDs, frozen champion reference. A SQLite checkpoint per campaign, keyed by campaign id; the campaign page and the CLI read the same rows.

Swapping an agent

Each agent method is a pure function from context to one Pydantic schema. The prompt is swappable; the returned schema is the contract; graph/routing.py and the node assertions are what make a bad swap fail loudly instead of quietly producing a worse campaign. Models are named provider:model_id and built only in src/amt/llm.py.

Three things a swap cannot do, because code and not the prompt decides them. It cannot widen the transform vocabulary: runtime_vocabulary() is rendered into the Planner's context and anything outside it lands infeasible. It cannot change an approved shape: _bind_feature_fit keeps the structural payload a human signed and takes only booster_params from the Trainer, recording the rejected ask. And it cannot upgrade a losing result: the conclusion's recommendation is clamped to the measured validation verdict, so prose may explain a loss but never promote it.

Rules enforced in code, not prose

  1. One contract per campaign. contract_hash is stamped at HC3; every node and every job asserts it before doing work.
  2. Splits are immutable. Jobs read VERSION AS OF and verify row counts against the contract.
  3. Train jobs cannot see QA. SplitGuard raises on any read outside the role's allow-list.
  4. The backlog is written once. After the baseline, approved at HC_BACKLOG; planner_select_hypothesis selects and never generates.
  5. An approved shape is final. execute_training refuses a config whose feature_fit_hash is not the approved one, and the Trainer's structural asks are clamped rather than bounced.
  6. A human reads every hypothesis. HC_CHAMPION interrupts once per hypothesis. The Trainer loop inside a hypothesis stays autonomous; the band between HC3 and HC4 does not.
  7. QA needs a freeze. Routing refuses Phase 0 unless exactly one FrozenChampion exists; the Trainer cannot re-enter after freeze.
  8. The proxy is checked before the candidate. A metric that does not track the product number for the ranker already in production cannot certify a new one.
  9. Same math for everyone. One versioned harness scores baseline, candidates and QA; QA loads the model through MLflow pyfunc, not the trainer's in-memory object.
  10. Bounded loops. The Trainer stops at max_iterations or the compute budget regardless of what the agent proposes, and a bit-identical retune reads as no_op and counts toward convergence.
  11. Compute is attributable. Every job cluster carries amt, amt_campaign_id, amt_role and amt_hypothesis_id, so a campaign's cost is a query against system.billing.usage rather than an estimate.
