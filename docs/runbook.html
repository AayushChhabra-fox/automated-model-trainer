Automated Model Trainer · operator guide

AMT Runbook

How to set up, start, supervise and close an experiment campaign. Seven moments need you; only the trainer loop inside a single hypothesis runs unattended. Companion docs in the repo: docs/SPEC.md, docs/PLAN.md, docs/campaign-map.html, and docs/RUN_FYL_CAMPAIGN.md for a worked campaign with the numbers to expect at each gate.

Two surfaces, one graph. amt web is the primary one: a local Flask app where you read each checkpoint's document in full, answer it, watch progress, and rewind a gate you already approved. The CLI does everything the browser does and is what you use for scripting, --mock runs and CI. Neither is a cache of the other — both read state through amt.monitor and write it through the same Command(resume=…), so they cannot disagree about a campaign.

1One-time setup

1.1 Databricks identity

AMT normally runs as a service principal. Create or reuse one and grant it:

Generate an OAuth secret for the principal under Workspace admin → Service principals → Secrets. Running as yourself instead: set DATABRICKS_TOKEN to a PAT and it takes precedence over the OAuth pair, which is the quickest way onto source data a principal cannot reach yet. The PAT needs the files scope or Volume uploads fail with does not have required scopes: files. Optional hardening: a second principal for QA jobs with SELECT on split_qa only (see PLAN.md §9; not wired by default).

Compute defaults to a per-run job cluster, and that is what makes cost attributable: tags are a property of a job cluster, so each run carries amt, amt_campaign_id, amt_role and amt_hypothesis_id into system.billing.usage.custom_tags. Job clusters are created in single-user mode so they can install the AMT wheel from a Unity Catalog volume. Pinning an existing all-purpose cluster still works and iterates faster, but see §6 for what it costs you.

Then check everything a campaign needs before it spends a cluster minute. MLflow reads credentials from the process environment rather than from Settings, so export .env in the shell you run amt from:

set -a && . ./.env && set +a

doctor verifies auth, the warehouse, a writable artifact volume, the job-cluster spec against the node types this workspace actually offers, the MLflow experiment root, that every source table is readable, and one real structured-output round-trip against your LLM. config prints the resolved settings, masked, with the source of each value. Read the source column: an AMT_* variable exported in your shell silently shadows .env, and that column is the only thing that will tell you.

1.2.1 Choosing an LLM provider

AMT is provider-agnostic: the agents only need a chat model that can return structured output. Name each agent's model as provider:model_id and the orchestrator builds the right client. Nothing else in a campaign changes when you switch providers.

Provider prefixReachesAMT_LLM_BASE_URL

anthropicHosted Anthropicignored
huggingfaceA Hugging Face Inference Endpointrequired
openai-compatAny other OpenAI-compatible server: vLLM, TGI, Databricks model servingrequired
AMT_LLM_API_KEY=<your provider key>
AMT_PLANNER_MODEL=openai:gpt-4.1
AMT_PROBLEM_SPEC_MODEL=anthropic:claude-sonnet-5      # mixing providers is fine

Unprefixed names still resolve (claude-* to Anthropic, gpt-* to OpenAI, org/name to Hugging Face), but prefer the explicit form. Whichever provider you pick must support structured output reliably — the agents fail the stage rather than accept a malformed contract.

1.3 Dry run — no Databricks, no LLM

uv run amt start "Improve homepage row ranking" -c dryrun --mock
uv run amt run   dryrun --mock       # drives every checkpoint inline

Or answer the gates one at a time, which is what a script would do:

uv run amt approve dryrun --mock     # HC2
uv run amt approve dryrun --mock     # HC3
uv run amt approve dryrun --mock     # HC_BACKLOG
uv run amt approve dryrun --mock     # HC_CHAMPION → QA → stops at HC4
uv run amt report  dryrun --mock
uv run amt promote dryrun --mock

If this completes, the orchestrator is healthy. Everything after this point is configuration and data.

Writes {catalog}.{schema}.demo_interactions (user_id, item_id, ts, item_genre). Run one real campaign against it before pointing at production tables.

2Running a campaign

A campaign is one frozen question. Its id is also the LangGraph thread id and the MLflow experiment name, so pick something you can find later — hp-rows-seq-2026q3, not test1.

uv run amt web        # http://127.0.0.1:5000 — the campaign list, and `new campaign`

The campaign page is the monitor: the pending checkpoint at the top with its verbs, the document of record in full underneath, then the hypothesis table, the experiment history and a live progress log carrying each Databricks run URL. It refreshes every five seconds only while a runner is live, so a page showing a checkpoint never reloads under your cursor. No auth, by design — it binds to 127.0.0.1 and runs with your .env, exactly as the CLI does.

Each step below gives the CLI equivalent, because the CLI is what you script.

2.1

Start HC1

uv run amt start "<problem>" -c <campaign> \
  --max-iterations 6 --max-hypotheses 2 --max-compute-minutes 240

Write the problem the way you would brief a new ML engineer:

  • the product surface and the decision the model makes there;
  • the source tables you believe are relevant, fully qualified;
  • the product metric you actually care about;
  • the current baseline, if one exists;
  • constraints — latency, cold-start, fairness, catalog rules.

The Problem Specification Agent probes the tables you name via read-only SQL (schema, volume, freshness, label availability, leakage), drafts a ProblemSpec, and stops at HC2. The budget flags are hard stops enforced by routing, not suggestions to the agent.

Which evaluation mode does your question need?

This is the single most important thing to get right in the problem statement. The contract's evaluation_mode records the choice, and both modes run through the same harness, the same paired bootstrap and the same freeze.

next_itemgrouped_rerank
A unit isOne user at a point in their historyOne render — one container shown to one user at one time, per the contract's group_key
CandidatesGenerated: popularity / random / mixed, n per unitlogged_impressions — what that render actually showed, so n never applies
RelevanceThe next item the user touchedThe conversion label on each impressed tile
BaselineA model: popularity, sasreclogged_order — the incumbent ranking itself
kA reporting choiceThe above-the-fold tile count. On CTV, 4
Answers"What should we show this user next?""Does a new ranker beat the order this rail already ships, on its own metric, over a recent window?"
Two things follow from choosing grouped_rerank. You are measuring re-ordering, not retrieval — the candidate set is the incumbent's, so the campaign cannot tell you whether better candidates exist. And position bias must be corrected or a ranker is rewarded for copying the incumbent: set relevance_weighting: pbm and materialisation estimates per-client, per-slot examination propensities from the train split alone, turning each label into a gain. Name the container, the page, the clients, the label column and the tile count in the problem statement — those are human-owned facts and the agent will not infer them.

In both modes the harness computes recall@k, ndcg@k, hitrate@k, mrr@k and coverage@k, plus auc, pr_auc, logloss and ece as secondary metrics only — the primary metric has to be one that moves the surface, and the contract's own validation refuses a pointwise diagnostic as primary.

2.2

Approve the ProblemSpec HC2

The CLI prints the spec as JSON. Check, in this order:

  1. Decision and target — is this the prediction the product needs?
  2. Data sources — right tables, grain, join keys, timestamp column?
  3. Label construction — matches how the product defines success, no leakage?
  4. Offline metric — one that plausibly moves the product metric?
  5. Baseline — the thing you would actually have to beat?
uv run amt approve <campaign>
uv run amt reject  <campaign> -m "Label should be completion >= 70%, not any play. Exclude autoplay events."

Reject as many times as needed; each rejection re-runs Stage 1 with your feedback. Once approved, the spec is frozen for the campaign.

2.3

Approve the EvaluationContract HC3

After HC2 the system drafts the contract, materializes the three splits as Delta tables, then stops. Check:

  1. Temporal boundaries — train / validation / QA windows don't overlap; the QA window is recent enough to matter.
  2. Population eligibility and exclusions — bots, internal users, minimum-interaction thresholds.
  3. Split references — delta_version, row_count, membership_hash all present.
  4. evaluation_mode, and if it is grouped_rerank: group_key, position_column, label_column, label_positive_values, relevance_weighting and the propensity floor. A wrong group_key here silently produces splits that look plausible and mean nothing.
  5. Metric definitions and harness_version — what you expect to report.
  6. product_metric_source — the external daily series QA will correlate against. Pick one built from a different source than your label, or the proxy check proves nothing.
  7. Acceptance criteria — the bar QA will hold the champion to, including min_proxy_correlation and the cohort-regression guardrail. Set it now; it cannot move later.
uv run amt approve <campaign>

Approval stamps contract_hash.

Rejecting at HC3 re-materializes the splits. If you realize the contract is wrong after training has started, do not edit anything — start a new campaign. That is by design: the same comparison must never silently continue on changed ground truth.
2.4

Approve the hypothesis backlog HC_BACKLOG

After HC3 the baseline runs and the Planner writes the campaign's whole backlog at once, then stops. This is the only point at which you see every hypothesis before compute is spent on any of them, and the backlog decides how the budget is spent.

In the browser this is a table with keep and drop boxes. From the CLI:

uv run amt show    <campaign>                  # the full backlog, not the panel preview
uv run amt approve <campaign> --keep H1,H3     # order sets run order; everything else is dropped
uv run amt approve <campaign> --drop H2        # or strike individually
uv run amt reject  <campaign> -m "all four ignore that titles turn over daily"

Read each hypothesis against what this campaign can actually run:

  1. Testable here — the design only needs the frozen splits, the contract's metrics, and transforms the FeatureRecipe can express.
  2. Falsifiable — falsification_criteria names a result that would kill it, not a hedge.
  3. Worth the compute — estimated_cost_minutes against max_compute_minutes, in the priority order you would want if the budget ran out early.
  4. Different from each other — variations of one idea waste hypotheses.
Prefer drop over reject. Dropping marks that hypothesis abandoned and keeps the rest intact; rejecting costs a full round trip through the Planner to redraft the whole backlog. Hypotheses asking for something the runtime cannot express arrive already marked infeasible with the reason — the Planner is given the literal transform vocabulary, candidate strategies and registry families as context, so that is caught before it costs a job.

Approval is once per campaign: the backlog is written once, and planner_select_hypothesis selects from it without ever generating more.

2.5

Approve every feature/fit shape, once HC_FEATURE

The gradient-boosting families (xgboost_classifier, xgboost_reranker, lightgbm_classifier, lightgbm_reranker) have no fixed input shape, so each needs a FeatureRecipe and a FitSpec. This gate shows you every approved tabular hypothesis's shape at the same time, before any job is submitted, and it interrupts once per campaign rather than once per hypothesis. If no surviving hypothesis is tabular, it does not interrupt at all.

uv run amt status  <campaign>               # awaiting HC_FEATURE
uv run amt show    <campaign>               # every shape, in full
uv run amt approve <campaign> --drop H3     # dropping a shape abandons its hypothesis
uv run amt reject  <campaign> -m "H1 reads the labelled event; build it from history only"

Read the table in this order:

  1. Leakage. Every feature must be computable at serving time from what is known before the decision. This is the one thing nothing downstream can catch for you.
  2. Estimated candidate rows. A plausible-looking n against a large validation split is tens of millions of rows of feature building, and nothing else in the payload says so. Under logged_impressions the candidate set is closed at what the surface showed, so n is never applied and the gate says so instead of pricing it.
  3. Duplicate shapes. A shape identical to another hypothesis's is annotated as such — two hypotheses with the same feature_fit_hash are one experiment run twice.
  4. The six FitSpec fields. Objective, eval metric, rounds, early stopping, negative sampling, seed. Not booster_params — those are the Trainer's to change without asking.

Approval stamps feature_fit_hash over the recipe plus the structural part of the FitSpec. Later iterations that only retune hyperparameters run without asking again, and execute_training refuses any config whose hash is not the approved one. popularity, sasrec and logged_order skip this checkpoint entirely.

A Trainer that asks for a structural change is clamped, not bounced: the approved shape is kept, only its booster_params are taken, and the rejected ask is recorded and shown in amt status. The old behaviour sent the campaign back through this gate on the agent's initiative, which is how a review turned into a loop.
If an approved shape turns out to be unexecutable — a recipe reading columns the split does not carry — do not reject something downstream. Rewind.
2.6

The autonomous band, and the champion review HC_CHAMPION

Between HC_FEATURE and QA the Trainer loop runs unattended within one hypothesis: propose a config, submit the job, interpret the result, iterate until it succeeds, plateaus, falsifies itself, repeats a config it already ran (no_op), or runs out of budget. Then it picks a champion for that hypothesis and stops.

This gate is per hypothesis, not per iteration, and it is on by default. It shows this hypothesis's champion against the baseline and against every prior champion on the primary metric and the contract's secondaries, cohort deltas, the budget left, and the Planner's recommended next move. The delta column against the baseline is the rightmost one — on the campaign page the table scrolls horizontally with the metric names pinned.

uv run amt approve <campaign>                  # continue to the next hypothesis
uv run amt approve <campaign> --drop H4,H5     # abandon hypotheses not worth the budget

In the browser there is also a freeze button: stop exploring, take the best champion so far and go to QA. Use it when a hypothesis has clearly answered the question and the remaining ones will not change the decision. --no-gate-champions disables the gate entirely, which is for rehearsal campaigns, not real ones.

While jobs run, watch the progress log on the campaign page — each Databricks run URL lands there. From a second terminal:

uv run amt status <campaign>

Key fields: stage, current_hypothesis_id, budget (iterations used / max), size of experiment_history, hypothesis_champions, frozen_champion, and two worth reading closely: gate_cycles, flagged above two, which means you and the agent are disagreeing rather than converging; and any clamped structural ask, which means the Trainer wanted a shape you did not approve.

In Databricks, open MLflow experiment /Shared/amt/<campaign>. Useful filters:

tags."amt.campaign_id" = '<campaign>' and tags."amt.role" = 'train'
tags."amt.role" = 'qa1'

Every run carries amt.hypothesis_id, amt.contract_hash, amt.config_hash, amt.harness_version. Each run's result.json artifact is exactly what the orchestrator saw.

Typical wall-clock: baseline 5–10 min; each training iteration 10–40 min depending on cluster and model family; QA phases 5–15 min each.

2.7

QA, the report, and the decision HC4

QA runs in two phases on the frozen champion. Phase 0 is integrity: the artifact loads through MLflow pyfunc, its schema matches, and it reproduces its own logged validation numbers. Phase 1 is the holdout — the only read of the QA split in the whole campaign.

Phase 1 checks the proxy before it looks at the candidate. It computes the incumbent's offline primary metric on daily slices of the QA split and correlates it (Spearman ρ) with the external product series the contract named. If ρ is below min_proxy_correlation, or there are fewer than seven overlapping days, the campaign is SPEC_REVIEW with that reason and no candidate number is displayed. A metric that does not track the product number for the ranker already in production cannot certify a new one.
uv run amt report <campaign>          # conclusion + MLflow references

The campaign page shows the headline rows inline and links the full HTML report, which is also logged to the final MLflow run as report.html. Its order is deliberate: proxy sanity first, then the effect in product units (top-slot conversions per 1,000 renders, candidate against incumbent, with an interval), then the offline delta and its CI, then the cohort table with regressions called out, then what an online test would cost — MDE at 80 % power, required renders, days at this surface's measured traffic. Every number comes from Phase1Result; the Planner writes the prose around them and never the numbers.

Read the conclusion as a paper, not a scoreboard.

QA decisionWhat it meansYour move
PASSFrozen champion beat the baseline on the untouched QA split within the predefined criteriaamt promote registers UC model {catalog}.{schema}.amt_<campaign> with alias candidate. Plan an online A/B or shadow test.
FAIL_HYPOTHESISWon on validation, did not generalizeRecord it. Do not rerun the same hypothesis with tweaks against this QA split. New hypothesis → new campaign.
SPEC_REVIEWThe labels, population or metrics are wrong, or the proxy-sanity gate failedFix the spec or contract in a new campaign; this one is closed.
INVALID_EXPERIMENTPhase 0 failed its capped number of times on a technical defectFix the artifact / inference bug in code, then start a new campaign.
uv run amt promote <campaign>                                   # PASS only
uv run amt promote <campaign> --model-name main.recsys.homepage_ranker

A negative result is a finished campaign. The MLflow final run holds the report either way.

The recommendation is clamped to the measured numbers: a champion that lost to the incumbent on validation reads hypothesis_rejected whatever the narrative says, and whatever QA did or did not manage to run. The prose may explain a loss; it cannot promote one.

3Rewinding, interruptions and recovery

An approved gate is final by design — the Trainer is clamped to the shape a human signed, and nothing downstream can reopen it. When the approved document itself turns out to be unexecutable, the honest remedy is to go back and approve a different one rather than let the run proceed on a shape that trains on nothing. That is a rewind, available on the campaign page under go back, or:

uv run amt rewind <campaign> --to feature -m "the recipe reads columns the split does not carry"
uv run amt rewind <campaign> --to backlog -m "every hypothesis assumes item identity carries over"
uv run amt rewind <campaign> --to qa      -m "the pyfunc signature dropped the candidates"
TargetRe-enters atCosts you
backlogafter the baseline, into planner_hypothesesThe backlog is redrafted. Mid-flight hypotheses return to pending and their budget slot comes back; abandoned ones stay abandoned, because a human struck them deliberately.
featureafter the approved backlog, into planner_feature_fitThe shapes are redrafted; the backlog stands.
qaafter the freeze, into qa_phase0Only QA's own results are cleared. The model is untouched — this is for an evaluation-plumbing fix, and nothing about the artifact changes.

Nothing that ran is erased: experiment_history and every MLflow run stay. Rewinding into training is refused once a champion is frozen — --to qa, or a new campaign, are the only honest paths then. The message is not paperwork; it is the feedback the Planner redrafts from.

Metric names: recall@k, ndcg@k, hitrate@k, mrr@k, coverage@k, with k taken from the contract's own metric list — {5, 10, 20} only when the contract does not say otherwise, so a contract asking for ndcg@4 is scored at 4. auc, pr_auc, logloss and ece appear as secondaries. Cohort keys look like history_length=cold_start, client_name=ROKU.

Mind the prefix. The harness emits bare metric names; the training job logs them under val/, and both spellings reach campaign state. Anything comparing a contract's primary_metric against a stored metrics dict goes through amt.schemas.run_result.metric_value, which accepts either — a raw .get looks like it works and silently returns nothing for half its inputs.

5Things the system will refuse to do

Enforced in code — routing, SplitGuard, hash assertions. If you hit one, the fix is a new campaign, not a workaround.

  • Run a training or baseline job with qa in its allowed splits.
  • Train a booster family on a feature/fit shape you did not approve, or on one that changed after you approved it. A structural ask from the Trainer is clamped, not honoured.
  • Generate new hypotheses after the backlog is approved, or select one that is abandoned or infeasible.
  • Report a candidate's QA numbers when the proxy-sanity gate failed.
  • Recommend promotion for a champion that lost to the incumbent on validation.
  • Run QA before exactly one FrozenChampion exists.
  • Re-enter the trainer after freeze, including by rewinding.
  • Continue after contract_hash changes.
  • Exceed --max-iterations or --max-compute-minutes.
  • Retry Phase 0 past its cap.

6Cost: attribution and guardrails

Every job cluster AMT submits carries four tags: amt=true, amt_campaign_id, amt_role (materialize / baseline / train / qa0 / qa1 / final) and amt_hypothesis_id. They land in system.billing.usage.custom_tags, so "what did this campaign cost" and "which hypothesis burned the budget" are queries rather than estimates. See .cursor/rules/databricks-cost.md for the query and the dashboard.

What pinning a cluster costs

Tags are a property of a job cluster. A pinned all-purpose cluster (AMT_EXISTING_CLUSTER_ID) can carry a static amt=true cluster tag — that part works, and its cost stays attributable to AMT — but amt_campaign_id, amt_role and amt_hypothesis_id vary per run and have nowhere to live, so per-campaign and per-hypothesis attribution is gone. It also bills at the All-Purpose rate: measured on this workspace, $0.650/DBU against $0.200 for Jobs Compute — 3.25×, not the "about twice" rule of thumb. Over the last 30 days the pinned cluster bought a third of the compute for the same money, and it is the untaggable third.

Set against that: a warm cluster skips the ~4.5 minutes a job cluster spends starting, which over a twelve-iteration campaign is about an hour. amt doctor reads the cluster and tells you which trade-offs apply, including two that are easy to miss — a runtime without -ml- in its name pip-installs the booster libraries on every run and those installs accumulate cluster-scoped, and a single-node cluster is fine for the boosters but slow for materialisation, which pushes the whole source table through Spark.

Pin one while you are learning the gates. Leave it unset for a campaign whose cost you want to attribute, and because materialisation wants the workers.

Other guardrails

  • Start with --max-hypotheses 1 --max-iterations 4; widen once the first campaign completes.
  • The Problem Specification Agent is capped at AMT_MAX_PROBE_STEPS (default 8) SQL probes.
  • AMT_MAX_CANDIDATE_ROWS (default 50M) is the budget HC_FEATURE prices each shape against.
  • Per-agent models can be downgraded — or pointed at a cheaper provider — via AMT_*_MODEL for rehearsal campaigns.

The four booster families share one runtime (src/amt/jobs/models/tabular_common.py) that executes the recipe: it builds (history, candidate) rows from the frozen splits plus the item-attribute tables the recipe names, fits the booster, and at serving time scores candidates through the same feature builder. Under logged_impressions the candidates come off the render row rather than being generated, so the recipe's column transform reaches impression-row fields — position, item metadata, user context — directly, and most first-campaign features need no new transform kind.

Each family declares its own dependency (requires_pip in the registry) and the executor passes it as a per-run library install, which is what makes job clusters viable. Locally they need xgboost / lightgbm from the jobs extra (on macOS also brew install libomp); the unit tests skip when the native library cannot load.

Adding a family

  1. Implement fit / recommend / pyfunc wrapper in src/amt/jobs/models/<family>.py following sasrec.py — or, for a recipe-driven family, a thin module over tabular_common.fit_family following lightgbm_reranker.py.
  2. Register it in src/amt/jobs/models/registry.py, with requires_pip if it needs a library, and in RECIPE_FAMILIES plus amt.schemas.feature_recipe.TABULAR_FAMILIES if it takes a recipe.
  3. The Planner reads the registry to know what exists, so no prompt edit is needed for it to be proposable.
  4. Unit-test under tests/unit/test_models.py; no Spark or Databricks needed.
  5. Change nothing in the harness — evaluation is model-agnostic by design.

8Quick reference

amt web                             # the primary surface: list, campaign pages, reports
amt doctor [--tables a,b]           # everything a campaign needs, before it spends a minute
amt config                          # resolved settings, masked, with the source of each value

amt start   "<problem>" -c <id> [--max-iterations N] [--max-hypotheses N] [--max-compute-minutes M] [--mock]
amt run     <id>                    # drive every checkpoint inline from one terminal
amt list                            # every campaign in the local checkpoint database
amt status  <id>                    # compact state + which checkpoint is pending
amt show    <id> [--key K]          # the checkpoint document in full, not the preview
amt approve <id> [--keep H1,H3] [--drop H2]
amt reject  <id> -m "<feedback>"    # re-runs the stage with your note
amt resume  <id>                    # continue after crash / kill
amt rewind  <id> --to backlog|feature|qa -m "<why>"
amt report  <id>                    # Scientific Conclusion + MLflow refs (HC4)
amt promote <id> [--model-name <uc.name>]   # HC4 decision; registers on PASS
amt demo seed [--users N --items N]

approve answers whichever gate is pending: HC2, HC3, HC_BACKLOG, HC_FEATURE, HC_CHAMPION or HC4. Add --mock to any of these for an offline dry run with no Databricks and no LLM.
